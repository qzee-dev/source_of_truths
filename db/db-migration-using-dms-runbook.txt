2) Landing zone placement

Best practice:
- Management account: org, billing, guardrails
- Shared services: logging, CI/CD, maybe secrets centralization
- Network account: transit, VPN, TGW, firewall
- Workload account: app, EKS, EC2, RDS, DMS

For your case:
- Database belongs in the workload-prod account
- not in management
- not in shared services
- not in public internet
- usually not in the app account if you have a separate database platform account, but for most teams the default is workload-prod

The practical default:
- account: workload-prod
- VPC: vpc-workload-prod
- subnets:
  - app: 10.20.10.0/24, 10.20.11.0/24
  - db: 10.20.20.0/24, 10.20.21.0/24
  - dms: 10.20.30.0/24, 10.20.31.0/24
- on-prem: 10.10.0.0/16

This is a clean AWS landing zone pattern.

3) Site-to-Site VPN design

This is the production approach:

- AWS side:
  - Virtual Private Gateway (VGW) or Transit Gateway
  - Customer Gateway (CGW) configured on-prem
  - IPsec tunnel
  - static route to on-prem CIDR

- On-prem side:
  - router/firewall that supports IPsec
  - static route to AWS VPC CIDR
  - public IP for AWS VPN tunnel
  - tunnel protection matching AWS policy

Important:
- Use private connectivity only
- One tunnel is not enough for strict production; use dual tunnels if possible

Routing:
- AWS route table for private subnets:
  - destination 10.10.0.0/16 -> VGW
- On-prem route table:
  - destination 10.20.0.0/16 -> VPN tunnel

This ensures both networks can reach each other privately.

4) IPsec policy best practices

Use an AWS-compatible strong policy.

Recommended production IPsec policy:

- IKEv2
- Encryption: AES-256
- Integrity: SHA-256
- PRF: SHA-256
- DH group: 14 or 16
- IKE lifetime: 28800 seconds
- ESP encryption: AES-256
- ESP integrity: SHA-256
- PFS: enabled (DH group 14 or 16)
- ESP lifetime: 3600 seconds

Example AWS-compatible policy:
- Phase 1:
  - Encryption Algorithm: AES256
  - Integrity Algorithm: SHA256
  - DH Group: 14
  - Lifetime: 28800
- Phase 2:
  - Encryption Algorithm: AES256
  - Integrity Algorithm: SHA256
  - PFS: DH Group 14
  - Lifetime: 3600

Important:
- match exactly with your on-prem VPN vendor
- if your firewall does not support these settings, use the nearest equivalent supported by both ends
- avoid weak algorithms like DES, 3DES, MD5, SHA1

5) AWS firewall rules to allow

On-prem firewall:
- allow outbound UDP 500 to AWS VPN public IP
- allow outbound UDP 4500 to AWS VPN public IP
- allow ESP (Protocol 50) to AWS VPN public IP
- allow return traffic from AWS subnet ranges

AWS side:
- security group for DMS must allow inbound DB port from on-prem source CIDR only
- security group for RDS must allow inbound DB port from DMS SG and app SG only
- no public ingress to RDS
- no internet route on DB subnets

Use something like this:

- VPC: 10.20.0.0/16

- db subnets:

- dms subnets:
  - 10.20.30.0/24
  - 10.20.31.0/24

Route tables:
- app route table:
  - 10.10.0.0/16 -> VGW
  - 0.0.0.0/0 -> NAT or Internet depending on app pattern
- db route table:
  - 10.10.0.0/16 -> VGW
  - no internet route
- dms route table:
  - 10.10.0.0/16 -> VGW
  - no internet route

Security groups:
- DMS security group:
  - inbound 5432/1521/3306 from on-prem source depending on source DB type
  - outbound to RDS port
- DB security group:
  - inbound from DMS SG
  - inbound from app SG
- App security group:
  - allowed to RDS port only from app servers
  - no direct internet exposure

7) RDS target design

For production:

- enable Multi-AZ

- enable performance insights if needed

For PostgreSQL:

- subnets: private db subnet group

8) DMS production design

Create:
- DMS replication instance in private subnet
- DMS source endpoint = on-prem source database
- DMS target endpoint = RDS target
- DMS task = Full Load + CDC
- validation enabled
- logging enabled

Source endpoint:
- server name: on-prem DB host
- port: 5432/1521/3306 based on DB
- username: migration user with needed privileges
- password: stored in Secrets Manager or secure vault
- SSL: enabled if supported

Target endpoint:
- RDS endpoint
- database name
- user with schema management rights
- encrypted connection where possible

Task settings:
- full load + change data capture
- validation on
- target table mappings
- only migrate required schemas/tables first
- keep DMS task logging enabled

9) Production migration runbook

This is the standard minimal-downtime process.

Phase 1: Pre-migration validation
- verify source DB version compatibility
- confirm supported source/target engine
- create schema migration plan
- identify long-running transactions
- identify unsupported data types
- validate app compatibility with target engine
- create a dedicated migration user
- gather DB size estimate
- determine cutover window
- test in lower environment first

Phase 2: Build network
- create VPC and subnets
- create VPN gateway, customer gateway, tunnel
- create route tables
- create security groups
- create NACLs
- confirm IPsec tunnel is up
- verify pings or DB connectivity over VPN
- verify no public route on DB subnets

Phase 3: Build RDS
- create DB subnet group
- create RDS instance
- configure security groups
- enable encryption and backups
- configure monitoring and alarms
- confirm connectivity from DMS subnet

Phase 4: Create DMS
- create replication instance
- create source endpoint
- create target endpoint
- validate endpoints
- create full load + CDC task
- allow task to run and capture initial load
- monitor replication lag

Phase 5: Pre-cutover validation
- compare counts for key tables
- compare row checksums for key tables
- verify data matches source
- run app-level smoke tests on target
- verify any stored procedures, triggers, or functions are compatible
- ensure app has no pending schema drift
- pause nonessential writes if needed

Phase 6: Near-zero downtime cutover
- stop application writes at the app or load balancer layer
- allow DMS to catch up remaining changes
- verify replication lag is near zero
- confirm app can connect to RDS
- switch app connection strings to RDS
- re-enable app traffic
- monitor DB health and application logs
- keep DMS running briefly for post-cutover validation

Phase 7: Post-cutover
- monitor replication lag for 24–72 hours
- keep DMS running for a short verification period
- remove test users and temporary routes if needed
- retain backup and rollback instructions
- keep snapshots and logs

10) Important reality check about downtime

There is no way to get truly zero downtime without:
- app-level dual-write logic
- blue/green application deployment
- load balancer cutover
- database-aware migration strategy

For most production systems, the right goal is:
- near-zero downtime
- short cutover window
- controlled rollback
- data validation

This is the standard.

C. main.tf
```hcl
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "workload-prod-vpc"
  }
}

resource "aws_subnet" "db" {
  count             = length(var.db_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.db_subnet_cidrs[count.index]
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "db-subnet-${count.index + 1}"
  }
}

resource "aws_subnet" "dms" {
  count             = length(var.dms_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.dms_subnet_cidrs[count.index]
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "dms-subnet-${count.index + 1}"
  }
}

resource "aws_subnet" "app" {
  count             = length(var.app_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.app_subnet_cidrs[count.index]
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "app-subnet-${count.index + 1}"
  }
}

resource "aws_db_subnet_group" "db" {
  name       = "workload-prod-db-subnets"
  subnet_ids = aws_subnet.db[*].id
}

resource "aws_security_group" "db" {
  name        = "db-sg"
  description = "RDS database access"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = ["10.20.10.0/24", "10.20.11.0/24"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_security_group" "dms" {
  name        = "dms-sg"
  description = "DMS access from on-prem"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = [var.onprem_cidr]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_db_instance" "postgres" {
  identifier             = "prod-rds-primary"
  engine                 = "postgres"
  engine_version         = "16"
  instance_class         = "db.t3.medium"
  allocated_storage      = 100
  max_allocated_storage  = 500
  storage_type           = "gp3"
  db_name                = "appdb"
  username               = "dbadmin"
  password               = "VeryStrongPassword123!"
  publicly_accessible   = false
  db_subnet_group_name   = aws_db_subnet_group.db.name
  vpc_security_group_ids = [aws_security_group.db.id]
  deletion_protection    = true
  skip_final_snapshot    = false
  multi_az               = true
  backup_retention_period = 7
  storage_encrypted      = true
}
```
