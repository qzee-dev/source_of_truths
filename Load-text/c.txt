The best way to use the number of concurrent requests for scaling is to convert it into an average per-instance metric and use a [CloudWatch Metric Math](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/using-metric-math.html) expression. [1, 2] 
If you try to scale based on the raw total number of concurrent requests (e.g., "scale up if total concurrency hits 1,000"), your system will break. Once you scale up from 5 instances to 10 instances, the total concurrency is still 1,000, causing AWS to endlessly scale up until you hit your maximum.
------------------------------
## Step 1: Use the Correct Metric Formula
To prevent endless scaling, you must calculate Average Concurrency Per Instance: [1] 
$$\text{Average Concurrency} = \frac{\text{Total Concurrent Requests (Active Connections)}}{\text{Number of Healthy Instances}}$$ 
## Step 2: Implement via AWS Target Tracking
The most efficient way to configure this in AWS is using an Auto Scaling Target Tracking Policy combined with CloudWatch Metric Math. This tells AWS: "Keep my average concurrent requests per instance at exactly X". [1, 2, 3] 
You configure the policy with two metrics: [2] 

   1. Metric A (m₁): ActiveConnectionCount (from your Application Load Balancer).
   2. Metric B (m₂): GroupInServiceInstances (the number of running instances in your Auto Scaling Group).
   3. Metric Math Expression: m1 / m2 [1, 2] 

## Step 3: Find Your Target Scaling Number
Do not guess the "200" number. Run a quick load test using tools like Apache Bench (ab) or Locust to determine your target:

* 
* Under Load: Run 500 concurrent requests against a single EC2 instance.
* Watch Latency: Note the point where response times (latency) spike or errors begin.
* Set Safety Buffer: If the instance begins to fail or choke at 300 concurrent requests, set your Target Tracking value to 200. This leaves a 33% safety buffer for traffic spikes while new instances boot up. [4, 5] 
* 

------------------------------
## 💡 The Alternative: Request Rate (RPS) vs. Concurrency
According to Little's Law, Concurrency = Throughput × Latency. [6] 
Because of this relationship, if your application's response time is highly predictable (e.g., it always responds in 50ms), you don't even need to track concurrent connections. You can use the built-in AWS ALBRequestCountPerTarget metric instead. It measures the number of requests per minute hitting an instance and requires zero custom math or configuration. [3, 7, 8] 

* 
* Use ALBRequestCountPerTarget (RPS) if your requests are fast, short-lived, and uniform.
* Use Active Connections (Concurrency Math) only if your application handles long-lived requests, like WebSockets, server-sent events, or long-running file uploads. [1, 7]
